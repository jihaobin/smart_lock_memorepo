# 注册验证码匿名访问修复设计

## 问题与根因

移动端注册流程通过共享 `ApiClient` 请求 `POST /auth/send_verification_code`。服务端控制器已使用 `@Public()` 将该接口声明为匿名接口，但客户端 `AuthManager` 的公开路径规则仅放行登录、注册、忘记密码和 `public/*` 路径。

未登录用户请求验证码时，请求尚未发送到服务端，就被 `ApiClient.request()` 的本地鉴权检查拒绝，并构造错误码 `2001` 和提示“请先登录”。

## 修复方案

在 `AuthManager` 的公开路径规则中精确加入 `/auth/send_verification_code`，使客户端判定与服务端 `@Public()` 声明保持一致。

本次不增加通用的“跳过鉴权”请求参数，也不重构前后端公开路由配置。精确补充路径能够以最小改动修复当前错误，同时避免意外扩大匿名访问范围。

## 请求流程

修复后，未登录用户在注册页请求验证码时：

1. `useAuthApi.sendVerificationCode()` 调用共享 `ApiClient`。
2. `AuthManager.isProtectedPath()` 将 `/auth/send_verification_code` 识别为公开路径。
3. `ApiClient` 不执行登录状态拦截，将请求发送到服务端。
4. 服务端全局 JWT Guard 读取 `@Public()` 元数据并放行请求。
5. 现有短信服务继续负责验证码发送及其业务错误处理。

## 错误处理

本次仅移除错误的客户端登录前置条件。服务端返回的手机号校验、发送频率限制、短信服务异常及其他业务错误仍沿用现有 `ApiClient` 响应处理流程，不改变错误码或用户提示。

## 测试

为 `AuthManager` 增加针对性单元测试：

- `/auth/send_verification_code` 在未登录场景下被识别为公开路径。
- 现有登录、注册和忘记密码接口仍为公开路径。
- 普通业务接口仍被识别为受保护路径。

测试先在当前实现上失败，再修改公开路径规则使其通过，并运行共享包相关测试和静态检查。

## 非目标

- 不修改服务端控制器、JWT Guard 或短信服务。
- 不修改注册页面交互和表单校验。
- 不重构完整的客户端认证状态管理。
- 不改变其他接口的公开或受保护属性。
